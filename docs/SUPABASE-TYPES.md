# Migrations and generated types

## The problem this file exists to prevent

`src/integrations/supabase/types.ts` is generated from the **live** database. It
had drifted to 27 tables while `supabase/migrations/` had grown well past that,
so most of the newer schema — `contact_messages`, `subscribers`,
`expense_claims`, `expense_lines`, `attendance`, `chart_of_accounts`,
`expense_categories`, `cost_centres` — was invisible to TypeScript.

The workaround that grew around it was `(supabase as any).from('whatever')`.
That cast does not just lose column types; it makes a query against a table
the database has never heard of compile cleanly. The contact form shipped that
way and nothing failed until a real visitor pressed Send and got
`404 (Not Found) — PGRST205`.

Two different faults produce that same 404, and they are worth telling apart
before reaching for a migration:

- **The table is not there.** `db push` was never run, or the file was never
  pasted into the SQL Editor. Check
  `information_schema.tables`.
- **The table is there but PostgREST has not noticed.** Its schema cache
  predates the DDL, so it answers 404 for a table that is present, has RLS
  enabled and carries the right grants. This is what actually happened to
  `contact_messages`. Fix with `NOTIFY pgrst, 'reload schema';` — every
  migration in this repo should end with it.

A third possibility, worth ruling out on a table that is genuinely missing from
the API: PostgREST returns 404 rather than 403 for a table the requesting role
has no privileges on at all, to avoid confirming it exists. Compare the
`information_schema.role_table_grants` rows for `anon` and `authenticated`
against a table that works.

So: apply migrations, reload the schema cache, regenerate types, delete the
cast. In that order, every time.

## Applying migrations

> **Do not run `supabase db push` against this project.** As of 2026-08-30 the
> migration histories have *no* entries in common:
>
> ```
> local files the remote has NEVER recorded : 108
> remote entries with no local file         : 36
> matched on both sides                     : 0
> ```
>
> The remote's `supabase_migrations.schema_migrations` holds 36 timestamps
> generated by Lovable, ending 2026-04-10; none match a file in
> `supabase/migrations/`. So the CLI believes every local migration is pending
> and `db push` would run all 108 against a database that already holds most of
> that schema — including `20260627130000_backfill_sales_report_ledger.sql`
> and the COGS/journal migrations. Re-running a backfill on an append-only
> financial ledger duplicates postings. There is no undo.
>
> Reconciling the two histories (`supabase migration repair --status applied`
> for the ones already live, after confirming each one table by table) is a
> deliberate piece of work someone has to sit down and do. Until then:

**Apply migrations one at a time, by hand**, through the dashboard → SQL
Editor. Run the whole file — the RLS policies at the bottom are not optional.

Read-only inspection of the live schema, when the CLI has access:

```bash
npx --yes supabase@2 db query --linked "select table_name from information_schema.tables where table_schema='public' order by 1;"
```

Note that CLI database access depends on the Supabase account's role. A member
account without the right privileges gets
`403 … does not have the necessary privileges` on `db query`, `db push` and
`projects api-keys` alike, and the dashboard is the only route.

After any DDL, PostgREST needs to pick up the new shape. The migrations end
with `NOTIFY pgrst, 'reload schema';` for this reason; if a table still 404s a
minute after it was created, that notify is what was missing.

## Regenerating types

```bash
npm run types:supabase
```

This overwrites `src/integrations/supabase/types.ts`. Review the diff — a table
disappearing from it means the migration that created it is not applied to the
project you generated against.

## `types.extra.ts`

`src/integrations/supabase/types.extra.ts` holds hand-written definitions for
tables the generated file does not know about yet, and re-exports a merged
`Database` type. `client.ts` imports `Database` from there, not from
`./types`.

It is a stopgap, and it is meant to shrink. After a regeneration, delete any
table from `types.extra.ts` that now appears in `types.ts` — the generated
definition is authoritative. When the file is empty, delete it and point
`client.ts` back at `./types`.

## Checking what is not applied

There is no local Postgres in this setup, so the cheap check is to grep for
tables the code queries and confirm they are in the generated types:

```bash
grep -rho "from(\"[a-z_]*\"\|from('[a-z_]*'" src | tr -d "from(\"'" | sort -u
```

Anything on that list missing from `types.ts` is either unapplied or
un-regenerated. Find out which before writing another `as any`.
